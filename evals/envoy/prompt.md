# Envoy surface evaluation

Use only README.md, `go doc .`, and public command/consumer behavior. Public command help may clarify the documented forms. Evidence from source files, implementation-only details, test utilities, and repository import declarations are outside the permitted evidence. Do not use source-viewing or search commands.

Keep the existing `evals/envoy/fixture/consumer` consumer API-only: its deterministic five-step API evidence is independent of the product CLI. The separate `evals/envoy/fixture/cli` external module holds canonical copies of the scalar input fixtures; the product commands below use the canonical `examples/root.xsd`, `examples/valid.xml`, and `examples/invalid.xml` paths.

The API-only consumer calls `ParseSchema`, `ValidateInstance`, and `GenerateGo`: `ParseSchema` must succeed, `ValidateInstance` must return nil for the valid instance and must return an invalid `Diagnostic` for the invalid instance, and `GenerateGo` must be called twice with byte-identical results. It checks `FailureInvalid` and compiles the complete returned Go source. The inventory is deterministic catalog metadata only; it is not schema or instance test execution evidence.

Run these fixed commands in order. Run every command twice and compare stdout, stderr, and numeric process status independently. Record each attempted step as `pass`, `fail`, `blocked`, or `unevaluated`; invalid validation is the expected status-1 case. Keep catalog inventory, package documentation, API consumer, product CLI, generated-consumer compilation, and environment prerequisites as separate evidence classes.

Preserve the captured stdout, stderr, numeric status, and repeat comparison for inventory, documentation, and the API consumer in their matching report sections; keep inventory execution status separate from its `unevaluated` catalog result.

Run the inventory from `evals/envoy/fixture`, `go doc .` and the product CLI commands from the repository root, and the API-only consumer from `evals/envoy/fixture/consumer`.

```sh
go tool conformance inventory -root .
go doc .
go run .
go run ./cmd/goxsd9 parse examples/root.xsd
go run ./cmd/goxsd9 validate examples/root.xsd examples/valid.xml
go run ./cmd/goxsd9 validate examples/root.xsd examples/invalid.xml
go run ./cmd/goxsd9 generate --package envoygenerated examples/root.xsd
```

The parse command must produce exactly `documents=1 components=2` on stdout, with empty stderr and status 0. Valid validation must be silent on both streams with status 0. Invalid validation must keep stdout empty, preserve the located stderr diagnostic's source identity, `XSD2001`, related schema location, and `xsd11-datatypes#integer` meaning, and return status 1. Generation must keep stdout as the complete generated bytes, keep stderr empty, and compare the repeated bytes without trimming or rewriting them.

These public product CLI commands provide the exact parse summary, silent valid result, and located invalid result required by the evaluation.

Write the first untouched generated byte slice to a temporary external module for the generated consumer and compile it with `go test ./...` and `GOWORK=off`. Do not add generated source to the repository or use implementation-only APIs, source files, test helpers, network resolution, broader schemas, or catalog metadata as execution evidence.

Record the result in `report.md`. Give documentation, api, command, generated-consumer, and environment separate failure classes. Keep inventory metadata and its expected-validity/status/headline fields separate from command execution, and keep boundary evidence separate.

The product CLI, direct-choice generation, broader schema/validation features, and W3C conformance scoring are separate evaluation boundaries.
